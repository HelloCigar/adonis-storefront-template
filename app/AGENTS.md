# Backend conventions

- Use the AdonisJS skill for framework changes, Lucid for database work, and Japa for tests.
- Public controller actions use `index`, `create`, `store`, `show`, `edit`, `update`, or `destroy`. Model a custom action as a focused resource controller using one of those methods.
- Group related controllers in domain folders (`account/`, `auth/`, `content/`, `settings/`). Use names local to the folder, such as `settings/members_controller.ts`, and reference the automatically generated nested barrel (`controllers.settings.Members`) in routes.
- Group models, services, transformers, validators, and middleware in domain folders too. Shared catalog and checkout entities belong to their own domains; seller-specific workflows belong under `seller/`. Keep global entry points, such as the exception handler, at their layer root.
- Use names local to the domain folder rather than repeating its prefix. Nested transformers generate namespaced frontend types such as `Data.Seller.Product`; update consumers through regenerated contracts when moving them.
- Controllers own request validation, authorization, HTTP/session concerns, transformer calls, and responses. A simple model lookup/list is fine inline.
- Move workflows beyond simple model loading into default-exported service classes in `app/services/<domain>/*_service.ts`: multi-model queries, transactions, business rules, and coordinated writes.
- Resolve application services through constructor injection with `@inject()` on the consuming controller, middleware, or service. Import injected classes as runtime values. Do not instantiate them manually, export service instances, or introduce a provider when automatic class resolution suffices.
- Services take explicit domain inputs (models, IDs, tokens, validated payloads), not `HttpContext`, requests, responses, or sessions. Keep request state out of shared service instances and serialize through transformers at the HTTP boundary.
- Preserve user/session ownership constraints and transaction boundaries when moving logic. Keep Inertia loaders lazy so partial reloads do not trigger unrelated queries.
- Preserve established route names and URLs during structural refactors. Change routes/controllers at the source and let the running dev server regenerate `.adonisjs`; never edit generated files manually.
- Verify behavior with focused functional tests and typecheck/lint. Test real database behavior for ownership, transaction, and relationship changes.
- User roles are the `UserRole` union (`customer`, `staff`, `admin`) exported by the account User model. Use its `userRoles` tuple for validation and generated transformer types for frontend consumers. `User.isStoreStaff` identifies staff and admins.
- Gate resources with domain Bouncer policies. Use `authorize` for controller checks and `allows` for frontend permission flags. Global user management is admin-only; policy checks must preserve self-protection and resource association rules even for admins.
- Reference policies by their generated names, for example `bouncer.with('SellerProductPolicy')`, instead of importing policy classes into controllers, middleware, or transformers. Adonis maintains the policy registry and types.
- This is one shared store. Staff and admins manage all products, collections, variants, images, and orders regardless of creator attribution. Never filter management queries by sellerId. Legacy sellerId columns retain historical creator attribution only. Account/profile/address/order self-service policies require the signed-in user's ownership for every role, including admins. Customers cannot enter the dashboard, inbox, or store-management routes.
- The existing seller/ folders, Seller* generated identifiers, and /seller URLs are compatibility names for store management, not a marketplace domain. Keep those URLs and route names stable. The former seller role is migrated to staff; new code must use staff.
